How Does the Edge-to-Server Vision Codebase Work?

Long image

A

Answer

A stateless edge capture layer streams resized JPEG frames over HTTP to a single-process FastAPI server. One worker thread runs CPU ONNX detection, tracking, and anomaly rules while two React consoles poll telemetry.

  1. edge/ owns capture, resize, and JPEG upload with zero inference on-device.
  2. server/ unifies frame inference (POST /frames) and synthetic events (POST /events) through ingest_detections().
  3. RuleEngine evaluates public and home rules per device_id using edge capture timestamps (ts).
  4. frontend/src/ serves both :5173 Analytics Console and :5174 Edge Emitter Deck from one React bundle.

How do runtime modules connect end to end?

Diagram structure
  • Edge Capture edge
  • FastAPI Ingest api
  • Worker and Rules cv
  • SQLite and Alerts store
  • React Consoles ui
  • edge → api · POST /frames
  • api → cv · queue(8)
  • cv → store · anomalies
  • ui → api · config, /events
  • api → ui · poll JSON/JPEG
  1. Edge Capture ↗

    VideoSource and EdgeEmitterController read webcam, MP4, YouTube, or RTSP and upload JPEG frames.

  2. FastAPI Ingest ↗

    server/app.py checks X-API-Key, 2 MB payload limit, and JPEG SOF dimensions up to 4096px.

  3. Worker and Rules ↗

    worker.py, detector.py, tracker.py, and rules.py run CPU ONNX detection and home/public rules.

  4. SQLite and Alerts ↗

    db.py persists WAL tables while alerts.py and agent.py fire webhooks, beeps, and LangGraph triage.

  5. React Consoles ↗

    AnalyticsApp (:5173) and EdgeEmitterApp (:5174) poll live telemetry and push runtime config.

What happens during frame ingestion vs event injection?

Diagram structure
  • Edge Emitter edge
  • FastAPI App api
  • CV Worker worker
  • Pipeline & Rules pipe
  • SQLite & Alerts db
  • edge → api · POST /frames (JPEG)
  • api → edge · 202 queued
  • worker → api · Pop frame from queue(8)
  • worker → pipe · ingest_detections(dets, ts)
  • edge → api · POST /events (JSON)
  • api → pipe · ingest_detections(dets, ts)
  • pipe → db · Debounced events + anomalies
  • pipe → api · Return anomalies

Both entry paths merge inside ingest_detections() under ingest_lock so POST /events tests rules identically to live inference. Frame metrics (frame_bytes, inference_ms, e2e_ms) are recorded only by worker.py after ONNXRuntimeDetector.detect().
